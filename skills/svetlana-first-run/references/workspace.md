# Корень Google Drive и состояние

```text
Помощник Светланы/
├── system/
│   ├── КОНТЕКСТ-ПРОЕКТА.json
│   ├── ПЕРСОНАЛИЗАЦИЯ.md
│   ├── operations/
│   ├── clients/
│   ├── bookings/
│   └── Проверка подключения        [Google Таблица]
├── Клиенты/
│   ├── Клиентская база             [Google Таблица, сначала пустая]
│   └── <имя и короткий client_id>/ [по мере регистрации клиентов]
├── Склад/
│   └── База данных склада          [Google Таблица]
└── Оперативная память              [Google Таблица]
```

Это схема для нового аккаунта. Ни одного реального ID разработчика, его таблицы, профиля или клиентской карточки пакет не содержит. Папки и файлы создаются только после её Google-входа и в её проверенном Drive. Запись в предоставленную папку из аккаунта разработчика не означает, что созданные файлы принадлежат Светлане.

Для нового развёртывания `system/BOOTSTRAP.json` локально содержит UUID `deployment_id`, выбранный корень и пошаговый журнал; сохраняй намерение перед запросом и полученный ID перед следующим. Повторный запуск перечитывает ID, MIME, имя, родителя и владельца. Одноимённые объекты без проверяемой принадлежности не присваивай автоматически. При потерянном ответе создания и отсутствии однозначного ID поставь `needs_review`: не создавай повторно по одному совпадению имени.

Нативная таблица может сначала создаваться в «Мой диск»: немедленно сохрани ID, получи текущего родителя, перемести этот файл в целевую папку, проверь `mimeType` и `parents`. Это два отдельных шага, и после сбоя перемещения не нужно создавать вторую таблицу.

## Если адаптер импорта не передал MIME

Для нового файла используй подготовленный и проверенный XLSX и штатный `import_spreadsheet` с `upload_mode="native_google_sheets"`. Если инструмент доказанно отклонил локальный путь **до запроса Google API** с ошибкой отсутствующего `source_file.mime_type`, доступен проверенный обход:

1. Запиши в локальный журнал ошибку до API и намерение загрузить временный исходник. Вызови `upload_file` для этого локального XLSX с явным `mime_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"` и целевой папкой. Сохрани возвращённый ID временного файла и проверь его MIME, имя и родителя.
2. Получи именно этот файл через `fetch(download_raw_file=true, include_base64=false)`. Используй возвращённый объект `file_uri` с подтверждённым MIME целиком: не заменяй его путём, `download_url` или строкой JSON.
3. Запиши намерение конвертации. Передай объект в `import_spreadsheet.source_file` с `upload_mode="native_google_sheets"` и названием. Целевая папка задаётся отдельным перемещением после импорта, если схема инструмента не поддерживает её напрямую. Сохрани ID нативного результата; проверь MIME Google Таблицы, фактические вкладки/ячейки и родителя. Если требуется перемещение, выполни отдельный шаг по уже полученному ID.
4. После подтверждённого результата удали только временный XLSX по сохранённому ID и проверь удаление. Нативную таблицу закрепи в контексте; повтор установки использует этот ID.

Обход применяется к установленной ошибке адаптера, а не к неизвестному результату записи. При потере ответа загрузки, конвертации или перемещения сначала сверяй журнал и фактические объекты; не повторяй создание через другой инструмент. Если среда не принимает возвращённый объект `file_uri`, сохрани `needs_review` и сообщи ограничение. Не публикуй исходник на стороннем хостинге ради ссылки для импорта.

## Контекст проекта

Контекст версии 1 пакета скиллов:

```json
{
  "schema_version": 1,
  "engine": "codex-google-skills",
  "deployment_id": null,
  "account_email": null,
  "accounts": {"drive": {"status": "unverified"}, "calendar": {"status": "unverified"}},
  "defaults": {"location": "Санкт-Петербург", "timezone": "Europe/Moscow"},
  "resources": {
    "root_folder_id": null, "system_folder_id": null,
    "clients_folder_id": null, "stock_folder_id": null,
    "client_sheet_id": null, "stock_sheet_id": null,
    "memory_sheet_id": null, "calendar_id": null,
    "operations_folder_id": null, "client_index_folder_id": null,
    "bookings_folder_id": null, "connection_test_sheet_id": null,
    "personalization_file_id": null
  },
  "draft": {},
  "profile": null,
  "profile_confirmed": false,
  "client_schema": {"sheet_id": null, "header_row": null, "columns": [], "mapping": {}, "status": "awaiting_example"},
  "setup": {"phase": "needs_connection", "checks": {}}
}
```

Не публикуй этот заполненный файл в GitHub. Сохраняй JSON по стабильному ID с чтением до и после обновления. Не затирай изменённые вручную/другой задачей значения старой копией. При отсутствии условной записи у инструмента выполняй шаги последовательно, признавай ограничение гонок; конфликт требует сверки, а не «последняя запись победила».

Для пустой складской таблицы предложи и согласуй минимальную структуру: вкладка `Материалы` (ID, наименование, вариант/фасовка, единица, подтверждённый остаток, минимальный запас) и `Движения` (operation_id, material_id, дата, тип, количество, единица, до, после, основание). Остаток без подтверждения остаётся пустым. Не заменяй предоставленную существующую схему этим шаблоном. Клиентские колонки создаются только после образца и согласования; пустой нативный файл существует уже до этого.

Для «Оперативной памяти» новой пустой таблицы используй колонки: дата/время, operation_id, тип, объект, проверенный статус, следующий шаг, ссылки. Не переноси в неё полные переписки и ненужные клиентские данные. Для существующей таблицы сначала прочитай её реальную схему.
